# Unitree G1 driver for SPARK

A thin bimanual wrapper over `unitree_sdk2_python` that gives SPARK's BT
executor a left/right-separated primitive surface.

## SDK choice and version

- **Repo:** `github.com/unitreerobotics/unitree_sdk2_python`
- **Commit pinned in this workspace:** `d72a9515` (merge of PR #152,
  pushed 2026-02-26).
- **Cloned to:** `~/spark/external/unitree_upstream/`
- **What it gives us:**
  - `rt/arm_sdk` LowCmd channel for upper-body joints
    (`example/g1/high_level/g1_arm7_sdk_dds_example.py`, the 7-DOF case;
    `g1_arm5_sdk_dds_example.py`, the 23-DOF / 5-DOF-arm case).
  - `LocoClient` RPC for legs (`BalanceStand`, `Damp`, `Move`, `SetStandHeight`).
  - `G1ArmActionClient` RPC for canned arm gestures (wave, kiss, ...).
  - `HandCmd_` / `HandState_` IDL --- usable for Dex3 hands on
    `rt/dex3/{left,right}/cmd` (topic names verified against
    `unitreerobotics/xr_teleoperate/teleop/robot_control/robot_hand_unitree.py`).
- **What it does NOT give us:**
  - No Cartesian / IK endpoint for arbitrary EE targets. We must pair the
    SDK with an external IK solver.
  - No formal full-body planner (MoveIt-style) --- only the low-level joint
    channel and the high-level FSM.
  - No collision avoidance between arms.

## Install (on a robot-attached host)

```bash
# 1. System deps for Cyclone DDS
sudo apt install build-essential cmake python3-dev

# 2. Conda env that SPARK already uses
mamba activate spark_conda

# 3. Unitree SDK
cd ~/spark/external/unitree_upstream
pip install -e .             # provides `unitree_sdk2py`
# (the package vendors cyclonedds; pip will pull a prebuilt wheel)

# 4. IK backend (one of):
mamba install -c conda-forge pinocchio    # recommended for first bring-up
#   --- or ---
pip install pyroki                        # already used for UR10e in SPARK
```

## Network / DDS setup (G1)

1. Wire a laptop / on-robot Jetson to the G1's "developer" Ethernet port.
2. Give that interface a static IP on the G1's subnet (typical: `192.168.123.X`,
   the robot itself is `192.168.123.161`). Confirm with the support page
   https://support.unitree.com/home/en/developer/Quick_start.
3. Set `net_iface` in `configs/g1_default.yaml` to the NIC name (`ip a`).
4. Multicast must be allowed on that NIC --- DDS uses it for discovery.
   Sometimes you need `sudo ip link set <iface> multicast on` and to ensure
   ufw / firewalld is not dropping `239.255.0.1`.
5. Verify with the upstream `read_lowstate` test:
   ```bash
   python unitree_sdk2py/test/lowlevel/read_lowstate.py <iface>
   ```

## Safety procedures specific to G1

- **Always start in `BalanceStand`.** Per upstream issue #108
  (https://github.com/unitreerobotics/unitree_sdk2_python/issues/108),
  full-body `rt/lowcmd` and the on-robot balance controller are mutually
  exclusive; the supported tabletop manipulation combo is
  `LocoClient.BalanceStand()` (legs) + `rt/arm_sdk` (arms). The driver
  enforces this via `safety.require_balance_stand` in the YAML.
- **Hand off cleanly.** When done, ramp
  `low_cmd.motor_cmd[kNotUsedJoint].q` from 1 back to 0 (see Stage 4 of
  `g1_arm7_sdk_dds_example.py:154-159`). `G1Driver.disconnect()` does this.
- **Waist torque is the weak link.** The 1-DOF waist yaw is the lowest
  rated joint on a 29-DOF G1 (~30 Nm continuous). Keep both arms
  symmetric in load and prefer to step the robot instead of twisting.
- **Fall-recovery interlock.** If the IMU pitch/roll exceeds ~30deg the
  on-robot FSM will trigger fall recovery and *ignore* arm_sdk commands.
  Do not push arm targets that move the CoM outside the foot polygon.
- **Cable tether for first bring-up.** Hang the G1 from its frame or run
  the safety tether for the first dual-arm test --- the on-robot balance
  controller does react to arm_sdk loads, but it has been observed to
  drift on heavy / asymmetric loads.

## Bimanual primitive contract (for the BT layer)

The SPARK BT executor (`spark_real/control/score_executor.py`) was written
for one arm + one gripper. The G1 contract extends it:

- Each BT leaf may carry an `arms:` tag with value `left`, `right`, or
  `[left, right]`. Single-arm leaves call `move_left_arm_to_joint` /
  `move_right_arm_to_joint`; dual-arm leaves call `move_dual_arm_to_pose`
  with two separate poses.
- Detection objects carry an `assigned_arm` field set by the LLM planner
  (or, fallback, by a side-of-midline heuristic). This is what kills the
  centroid-merging failure mode (see paper §6): the planner now emits two
  separate `move_to_keypoint` leaves with distinct object IDs, and the
  perception layer is *forbidden* from merging detections across the two
  assigned arms.
- The new primitive `bimanual_grasp(left_object, right_object)` runs both
  arms simultaneously through approach -> open -> descend -> close.
  Synchronisation is handled inside the driver via the same 50 Hz writer
  thread (one tick publishes both arms together).

## What is missing for a real-robot bimanual demo

1. **IK pipeline.** Highest priority. Three options:
   - **Pinocchio dual-chain (recommended).** The
     `Robotics-Ark/ark_unitree_g1` repo ships a reference single-arm IK
     (`tests/test_demo/robot_arm_ik.py`). Extend to two chains sharing
     the chest/waist as the root. ~1-2 days of work.
   - **Pyroki dual-chain.** SPARK already uses `pyroki` for UR10e
     orientation-constrained IK (see `main.tex:126`). The library
     supports multi-chain robots via stacked task costs; we need to write
     a `G1DualArmIK` class with one cost block per arm and an optional
     coupling cost on `WaistYaw`. ~3-5 days including tuning.
   - **DRAKE.** Heaviest, but the only one with formal collision
     constraints between the two arms. Probably overkill for v1.
2. **Hand support is stub-only.** `set_left_gripper` / `set_right_gripper`
   send uniform closure on all 7 Dex3 motors. For real manipulation we
   need per-finger targets (pinch, hook, tripod) --- the
   `xr_teleoperate/robot_hand_unitree.py` retargeting code is the
   reference. Also need to verify whether the SKU is Dex3-1 (multi-finger)
   or the simpler 1-DOF G1 parallel gripper.
3. **Camera bring-up.** YAML lists topic names but they are TODO --- need
   to be confirmed against the actual head/wrist cameras shipped with the
   G1 unit. Likely `realsense_ros2` or Unitree's own image bridge.
4. **Network / NIC.** Static IP assignment, multicast, firewall.
5. **URDF + meshes.** We need the G1 URDF on this workstation for the IK
   solver and for visualization. `Robotics-Ark/ark_unitree_g1` ships
   `urdf/g1_description.urdf`; alternatively fetch from
   `unitreerobotics/unitree_ros` (the ROS 1 package, but the URDF is
   distribution-agnostic).

## Bimanual fix --- how this controller kills `centroid_merging`

The paper (§6) identifies that SPARK's perception layer collapses two
detections of *different* objects whose 2D centroids fall within 30 px of
each other (see
`spark_real/perception/spark_perception.py:643-660`,
the `CROSS_LABEL_CENTROID_PX = 30` block). That heuristic is correct for a
single-arm robot --- two prompts hitting the same object usually do mean
"same thing". On a bimanual robot we deliberately want two separate
detections for two arms even when their bounding boxes overlap.

The driver does *not* fix perception directly --- that change lives in the
perception layer. But the driver makes the fix actionable: it gives the BT
executor two channels (left arm + right arm) that the LLM planner can
route detections through. The planning pipeline becomes:

```
SAM3 detections --(LLM assigns arm: L|R|both)--> arm_assigned detection
arm_assigned detection -- (no cross-arm centroid merge) --> per-arm pose
per-arm pose --> g1_driver.move_dual_arm_to_pose(L, R, ik)
```

The 30-px centroid merge is now suppressed *only* when both detections
have the same `assigned_arm`. Detections with different `assigned_arm`
are kept separately and routed to different physical arms.

## Open questions for the user

1. **SKU?** G1-EDU 29-DOF (both wrists + dex hands) vs. G1-base 23-DOF
   (no wrist pitch/yaw, parallel gripper)? This changes both DOF and
   gripper handling.
2. **Hands?** Dex3-1 multi-finger, the 1-DOF parallel gripper, or none?
3. **Compute?** On-robot Jetson Orin, off-robot workstation over ethernet,
   or both? The 50 Hz writer thread is cheap (<5% of one core) but the
   perception stack will not fit on the on-robot Jetson without heavy
   quantization.
4. **First demo scope?** Static tabletop bimanual handover, or full
   walk-up-and-grasp? The latter requires the locomotion FSM + arm_sdk
   handoff to be tested, which is a separate workstream.

## Mock / DDS-loopback smoke test

Unitree ships a MuJoCo bridge (`unitree_mujoco`) that publishes the same
DDS topics as a physical G1. To test without a robot:

```bash
# 1. Clone the mujoco bridge
git clone https://github.com/unitreerobotics/unitree_mujoco
# 2. Start it with the G1 scene
cd unitree_mujoco && python sim/python/unitree_mujoco.py --robot g1
# 3. In another terminal, run our driver
python -c "
from spark_real.robots.g1.g1_driver import G1Driver
import numpy as np
with G1Driver(net_iface='lo', enable_hands=False) as g1:
    g1.balance_stand()
    g1.set_arm_sdk_enable(1.0)
    g1.move_left_arm_to_joint(np.array([0, 0.3, 0, 0.9, 0, 0, 0]))
    g1.move_right_arm_to_joint(np.array([0, -0.3, 0, 0.9, 0, 0, 0]))
    print(g1.read_dual_state())
"
```

If `unitree_mujoco` is not available the driver will block in `connect()`
waiting for `LowState_` for 10 s and then raise. That is the expected
failure mode for "no robot, no sim" --- proceed to install one.
